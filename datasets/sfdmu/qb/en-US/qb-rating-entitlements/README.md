# qb-rating-entitlements Data Plan

SFDMU data plan for the per-product usage terms on each QuantumBit product usage resource
(PUR): the **policies** that rate it (`ProductUsageResourcePolicy`, PURP) and the **grants**
it entitles (`ProductUsageGrant`, PUG). It runs right after [`qb-rating`](../qb-rating/README.md),
which creates the usage definitions, the policy records these point at, and the PURs themselves.

## CCI Integration

| Flow | Step | Task |
|------|------|------|
| `prepare_rating` | 3 | `insert_qb_rating_data` (qb-rating: definitions and PURs) |
| `prepare_rating` | **4** | **`insert_qb_rating_entitlements_data`** (this plan) |
| `prepare_rating` | 10 | `activate_rating_records` (activates the PURs and grants) |
| `extract_rating` | 2 | `extract_qb_rating_entitlements_data` |

`test_qb_rating_entitlements_idempotency` runs the extraction round-trip against an org that
already has qb-rating loaded.

## How the children match: `ProductUsageResourceId`, resolved per org

PURP and PUG match on the direct lookup `ProductUsageResourceId` (both are one per PUR in this
dataset). They can't match on the parent's portable key: on SFDMU 5.8.0 a child keyed on
`ProductUsageResource.Product.StockKeepingUnit` gets a target query with the
`ProductUsageResource.` prefix dropped ("Didn't understand relationship 'Product'"; upstream
issue #1218), so `Upsert` fails.

The tracked CSVs stay portable. They carry the parent's key as two traversal columns,
`ProductUsageResource.Product.StockKeepingUnit` and `ProductUsageResource.UsageResource.Code`,
and **no Ids**. [`parent_id_lookups.json`](parent_id_lookups.json) declares the lookup, and
`LoadSFDMUData` resolves it before SFDMU runs (`scripts/sfdmu_id_lookups.py`):

1. Copy the plan to a temp directory (the tracked files are never written).
2. Query the target org: `SELECT Id, Status, Product.StockKeepingUnit, UsageResource.Code FROM ProductUsageResource`.
3. Write `ProductUsageResource.csv` (Id, Status), which the plan declares `Readonly` with
   `externalId: Id`, and fill `ProductUsageResourceId` in every child CSV, root and pass 2.
4. Run SFDMU on the temp copy.

When a key matches more than one PUR (a Draft copy next to the Active one), the Active one wins,
then Draft. A remaining tie, or a key with no PUR on the org, **fails the load** and names the
key: load qb-rating first, or remove the extra copy.

Extraction runs the same lookup backwards. `ExtractSFDMUData` (and the idempotency round-trip)
extracts with Ids kept, then turns each child's `ProductUsageResourceId` back into the two key
columns, because SFDMU drops a child's 2-hop traversal columns on extract. The processed output
matches the tracked CSVs row for row.

When #1218 is fixed upstream, this plan can key the children on the parent's traversal key
directly and drop the lookup file.

## Passes: insert missing rows, then correct existing ones

| Pass | PURP / PUG | Why |
|------|------------|-----|
| 1 | `Upsert` + `skipExistingRecords: true`, full CSV including PUG `Status=Draft` | Inserts what's missing; never touches an existing (Active) row |
| 2 | `Update`, PUG without `Status` (`objectset_source/object-set-2/`) | Corrects the other fields of existing rows; Status is never sent |

Status is required when a grant is inserted, and sending `Draft` to an Active grant demotes it
silently, so it's only ever written on insert. `activateRatingRecords.apex` activates.

The policy and unit objects, Product2 and the PUR are `Readonly` in both passes: qb-rating owns
them, and each pass must declare the lookups its rows resolve (an undeclared lookup is sent as
null on Update).

**Reloading a built org** (live-verified 2026-10-30) changes nothing: 23 PURP and 12 PUG report
"Same data", and nothing is deleted or demoted. A corrected value in a CSV (e.g. a grant
`Quantity`) lands through pass 2. The platform locks some fields on Active records; when it
rejects one, the load fails with its message instead of skipping the row. Moving a row to a
different PUR adds a new record and leaves the old one, because nothing is deleted.
