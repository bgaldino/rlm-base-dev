# q3-rating-entitlements Data Plan

SFDMU data plan for the per-product usage terms on each Q3 product usage resource (PUR): the **policies**
that rate it (`ProductUsageResourcePolicy`, PURP) and the **grants** it entitles (`ProductUsageGrant`, PUG).
It runs right after [`q3-rating`](../q3-rating/README.md), which creates the usage definitions, the policy
records these point at, and the PURs themselves. It has the same shape as
[`qb-rating-entitlements`](../../../qb/en-US/qb-rating-entitlements/README.md) (todo 319).

## How the children match: `ProductUsageResourceId`, resolved per org

PURP and PUG match on the direct lookup `ProductUsageResourceId`; each is one per PUR in this dataset. They
can't match on the parent's portable key: on SFDMU 5.8.0 a child keyed on
`ProductUsageResource.Product.StockKeepingUnit` gets a target query with the `ProductUsageResource.` prefix
dropped (upstream issue #1218), so `Upsert` fails.

The tracked CSVs stay portable. They carry the parent's key as two traversal columns,
`ProductUsageResource.Product.StockKeepingUnit` and `ProductUsageResource.UsageResource.Code`, and **no
Ids**. [`parent_id_lookups.json`](parent_id_lookups.json) declares the lookup. `LoadSFDMUData` resolves it on
the target org into a temp copy of the plan before SFDMU runs (`scripts/sfdmu_id_lookups.py`). A key that
matches no PUR, or two PURs with the same status, **fails the load**; an Active PUR wins over a Draft one.
Extraction maps the Ids back to the two key columns.

## Passes: insert missing rows, then correct existing ones

| Pass | PURP / PUG | Why |
|------|------------|-----|
| 1 | `Upsert` + `skipExistingRecords: true`, full CSV including PUG `Status=Draft` | Inserts what's missing; never touches an existing (Active) row |
| 2 | `Update`, PUG without `Status` (`objectset_source/object-set-2/`) | Corrects the other fields of existing rows; Status is never sent |

The policy and unit objects, Product2 and the PUR are `Readonly` in both passes. q3-rating owns them, and each
pass must declare the lookups its rows resolve.

## Grants left out

The former q3-rating `ProductUsageGrant.csv` had 30 rows. 23 of them had no PUR. In the source org those grants'
product usage resource, product and usage resource are all blank. On 264 `ProductUsageResourceId` is required,
so those rows were rejected on every build. A grant without a PUR can't be keyed for a reload either. The owner
dropped them (todo 319). This plan keeps the 7 grants that have a PUR.
