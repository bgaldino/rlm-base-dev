# q3-pcm Data Plan

> **Shared records follow qb (todo 325).** Where q3 and qb load the same reference record, q3 uses qb's key and values, so the two shapes layer into one org: units `EACH`, `GB`, `MB` and `m` and classes `CAS01`, `DATAVOL` and `TIME` as qb-pcm defines them, and qb's selling-model names (One-Time, Evergreen Monthly, Evergreen Annual, Term Monthly, Term Annual). The 'Processor' attribute category uses qb's code `AC-QB-CPU`, and q3's own subscription attribute (Enterprise or Business, unlike qb's Evergreen or Term Based 'Subscription Type') is named 'Subscription Tier' (developer name `SubscriptionTier`), since both are unique in an org; its label stays 'Subscription Type', which is what the configurator shows and needn't be unique. Records qb doesn't have stay q3's own. An org loaded with q3 before todo 325 has the old selling models, units and classes; a reload adds the renamed selling models, units and classes beside them, and fails to add the 'Processor' category under its new code because the old `PRO` record holds the org-unique name, so rebuild it rather than reload it.

> **A load that fails partway needs cleanup, not just a reload (todo 330).** When a parent row is rejected, SFDMU still inserts the children that look it up, with that lookup blank. Several lookups in this plan are create-only, so a reload can't set them: `ProductAttributeDefinition` and `ProductClassificationAttr` `AttributeCategoryId`, `ProductRelatedComponent` `ChildProductId` and `ParentSellingModelId`, and `ProductSellingModelOption` `ProrationPolicyId` (the full list is in the sfdmu-data-plans skill, *Reloading a Plan Into a Live Org*). Fix the cause, delete the children that run inserted with the lookup blank where the CSV has a value, then reload. Check the result with `scripts/sfdmu_product_view.py`.

## Notes

- **ProductRampSegment loads in two passes.** Each pass reads the same `ProductRampSegment.csv`
  through a `sourceRecordsFilter`: pass 1 takes every segment except `FreeTrial`, and pass 2 takes
  `FreeTrial`. The platform rejects a FreeTrial segment until its product has a Yearly or Custom
  segment, and within one batch that segment doesn't exist yet. This was measured on a fresh 264
  build (todo 319). Pass 2 declares Product2 and ProductSellingModel `Readonly`, so the segment
  lookups resolve. `extract_q3_pcm_data` extracts pass 1 only (`object_sets: "[0]"`): pass 2 would
  re-extract those parents with only Id and Name and overwrite pass 1's files.
- **`ProductCategoryProduct.IsPrimaryCategory`** is `false` in every row. On 264 the field takes a
  boolean, and a blank value is rejected.
- **APTRG001 (AI Specialist Training) has no category.** It is sold only with other products
  (`IsSoldOnlyWithOtherProds`), and 264 rejects a category assignment for such a product. The
  source org kept both from before the rule existed (todo 319, owner decision).
- The source org's `Unit` UnitOfMeasureClass had no `Type`, which 264 requires. Nothing references
  it, so it was dropped (todo 319).
