# Account & Demo Utilities

This bundle ships demo-support utilities deployed via `deploy_post_utils` in both the `quantumbit` and `tso` flows. It provides account reset, decision table management, expression set management, search index rebuild, usage data tools, and quick-action shortcuts.

## Account Reset

The primary utility: a screen flow + Apex invocable that deletes transactional data from an account so it can be reused for demos without re-creating it.

**Entry point:** QuickAction `Account.RLM_Reset_Account` → Flow `RLM_Account_Utilities` → Apex `RLM_AccountUtilities.delAccountRelatedObjects`

### Two paths

Which path a reset takes depends only on who runs it (todo 397; owner decision "Admins keep main's engine"):

| Who | Path | What it does |
|-----|------|--------------|
| A user with both **Modify All Data** and **View All Data** | The engine in `RLM_AccountUtilities` | Deletes in two phases (see *Admin path*). What it cannot delete is kept and listed when it finishes. An account with heavy usage may need several runs; each one keeps its usage deletes, and the result says when to run it again |
| Anyone else, such as the salesrep persona | `RLM_AccountResetPlan` | Builds one deletion plan and checks it first (see *Non-admin path*). If the user cannot delete every planned record, the reset does not run and changes nothing, and the result lists why. Otherwise it deletes exactly the plan, all or nothing, in one run |

### Flow screen options

| Option | Default | Behavior |
|--------|---------|----------|
| Delete Assets | true | Removes assets, asset relationships, asset rate card entries (`AssetRateCardEntry`), the binding object rate card entries sourced from the assets (`SourceAssetId`, whatever they are bound to: live 264, one blocked the asset's delete), and the work orders (and cases, where the org has `Case.AssetId`) that reference the assets. The broader usage teardown runs regardless of this option. |
| Delete Fulfillment | true | Removes the account's fulfillment orders with their line items, the fulfillment plans of its orders with their steps, and its fulfillment assets with their decomposition records |
| Delete Billing | true | Removes the account's debit memos with their lines, then its invoices with their payment schedules, generated documents (`DocumentGenerationProcess`) and files, then its credit memos, canceling posted ones first. Invoices that are not Draft or Canceled need the **Delete Invoice and Invoice Lines** permission (`BillingInvoiceSuperUser`, from `RLM_DeleteInvoices`, in the `RLM_RCB` group), and credit memos **Allow Revenue Records Deletion** (`DeleteRevenueRecords`, from the managed Billing Admin set, also in `RLM_RCB`). On the admin path, invoices without that permission and invoices still processing are kept and listed; on the non-admin path, either stops the reset from running. Posted and void debit memos, and payments, are never deleted: Salesforce does not allow it |
| Delete Collection Plans | true | Removes the account's collection plans with their plan items, promise-to-pay payment schedules and cases (`Case.SourceId`), and the account's disputes, including disputes raised against its invoices, with their dispute items and cases (`Dispute.CaseId`). Only the account's own cases are deleted, and only those of a plan or dispute the reset deleted. With this option off and Delete Billing on, plans and disputes stay but lose their links to the deleted invoices |
| Preserve Contracts with Contracted Prices | false | When checked, contracts that have at least one `ContractItemPrice` child are kept, with the binding object rate card entries and usage resource policies bound to them (with Delete Assets, except an entry sourced from an asset the reset deletes, which goes with the asset); contracts without contracted prices are still deleted |

Whatever the options, every reset deletes the account's usage summaries, entitlements, buckets and transaction journals, its billing schedule groups, orders, quotes (with their files and generated documents) and opportunities. It also deletes the binding object rate card entries bound to the account and to the contracts it deletes, and the usage resource policies bound to the account, to the contracts it deletes and, with Delete Assets, to the assets. A contract or asset the reset keeps keeps its own, except a kept contract's rate card entry sourced from an asset the reset deletes, which goes with the asset.

### Admin path

For a user with Modify All Data and View All Data. The engine runs in two phases:

1. **Pre-savepoint (convergent):** usage resource policies (of the account, the contracts the run deletes and, with Delete Assets, the assets), the rate card entries bound to the account itself, and the usage summary graph. These operations are idempotent, so partial progress survives a later failure.
2. **Transactional (savepoint-wrapped):** entitlements, journals, collection plans and disputes, billing, fulfillment, contracts with their rate card entries, orders (those not in Draft set back to Draft first), assets with their rate card entries, quotes, and opportunities. Collection plans and disputes go before billing because deleting an invoice clears a dispute's link to it. If a step fails, the whole phase rolls back and the result says so; only the usage records from phase 1 stay deleted, and a kept asset keeps its rate card entries. A record that refuses a best-effort delete is reported as not deleted, with the platform's reason, instead of failing the run.

A governor limit would roll back both phases, so the reset stops short of one. Each delete is clamped to the DML rows left, and leaves two DML statements: phase 2's savepoint and its rollback each count as one (measured live 264). The usage teardown stops while the queries phase 2 needs are still available. Before the loop, the path switch's permission read takes one query, the one query this engine spends that the version before the two paths did not; no other read tells whether the user has Modify All Data and View All Data. A run that stops in phase 1 returns a result asking for another run, which resumes from the smaller graph. A run that stops in phase 2 keeps nothing from phase 2. The result asks for another run when phase 1 deleted usage records this run, which leaves the next run more room. Otherwise it says a rerun stops at the same point, and to delete some of the records in the largest groups first; either way it names the three largest groups phase 2 reached, by object and count. Asset rate card entries are deleted in phase 2 with their assets, so an account whose asset entries and the rest of phase 2 exceed the 10,000 DML rows of one run stops there on every Delete Assets run until some are deleted.

Known limitations of this path: an entitlement held by a bucket kept for another account's entitlement stays, so an asset it is bound to cannot be deleted, and a Delete Assets run rolls phase 2 back with the platform's reason. And an order with a line that another account's entitlement refers to cannot be deleted; orders are deleted best effort here, so it is reported as not deleted. The non-admin path refuses either up front and names the asset or order.

### Non-admin path

For anyone without both Modify All Data and View All Data. First, if the user cannot see the account, the reset does not run, and the result says only that. Otherwise the reset builds one deletion plan: for the selected options, the exact records each step deletes or changes, read once, in system mode, with one set of queries (the bucket tree included, however deep). The plan is checked before anything changes, and the deletes then remove exactly the plan's records, so a record is never deleted without having been checked (owner decision: refuse the whole reset). The reset does not run, and changes nothing, when any planned record:

- belongs to an object the user cannot read (counted, never named);
- is not visible to the user, or has no `UserRecordAccess` row (counted, never named);
- belongs to an object the user has no permission to delete (named; for credit memos the permission is Allow Revenue Records Deletion);
- cannot be deleted by the user, read from `UserRecordAccess`, 200 records a query (named). Files are the exception. Live 264, as the salesrep persona, `UserRecordAccess.HasDeleteAccess` was false for a file the persona owned, yet the delete succeeded, while another user's file was refused. So a file counts as deletable when the user owns it;
- needs a permission the user lacks (named): Edit Activated Orders for an activated order, Delete Activated Contracts for an activated contract, Access Lifecycle-Managed Assets for a lifecycle-managed asset, or Delete Invoice and Invoice Lines for a posted invoice;
- is an asset, with Delete Assets, that an entitlement kept for another account's data is bound to (named): run the reset with Delete Assets off;
- is an order with a line that another account's usage entitlement, or one held by a bucket kept for another account's entitlement, refers to (`OrderItemId`; named). Measured live 264: such an entitlement blocks deleting the line and its order;
- is an invoice still processing (named).

The same measurement found no such gap for orders: an activated order the persona owned, with Edit Activated Orders, read `HasDeleteAccess` true. Permissions are read from `UserPermissionAccess`. The billing and lifecycle ones are each read in a query of their own, so an org or release without one of those fields reads that permission as missing and nothing else.

A record is named only when the user can see it. The result says the reset was not run and lists those records by object with the reason, for example `Orders: 1 (no delete access to these records: 00000123); Opportunities: 1 (not visible to the user running the reset)`. The advice fits each kind of blocker. For a permission or record access, it advises asking a user with the named permission or access to run it, or having the records reassigned (Modify All Data covers record access, not the named permissions). For an asset or order that a kept entitlement refers to, which no permission or reassignment fixes, it says to run the reset with Delete Assets off (the asset) or have the other account's entitlement removed first, and that a user with Modify All Data and View All Data can reset the rest, the order reported as not deleted. The other account's entitlement is described, not named: it is that account's record. When the only blockers are invoices still processing, it says instead that some records cannot be deleted yet, and to run the reset again once the invoices finish processing. Live 264 the reason this check is needed: a query in a class that runs without sharing saw only the records sharing showed the salesrep persona, and a delete of a record the persona could edit but not delete was refused.

**Size limit, and all or nothing.** The non-admin path never deletes part of an account. The plan does all of the run's reading. Each of its queries requires one to spare beyond five kept for the decision table refresh the flow runs afterwards; live 264 that refresh took one query. Each read, the file lookups and the per-record access reads included, is also bounded by the query rows left and by what the heap left can hold, and the check first requires heap for the maps it builds from the planned rows. A plan whose rows exceed the DML rows left is refused too. In any of these cases the reset does not run, changes nothing, and says the account has too many records for a reset by this user, and that a user with Modify All Data and View All Data can run it. When the plan fits, the deletes run inside one savepoint. Every planned usage row goes first, those bound to the assets included (with Delete Assets): its delete constraints are circular, so the rows are retried round after round until a round removes nothing. No entitlement is then left to block an order line or an asset. Records outside the usage graph that point at usage rows were swept from the org's describe (live 264): a record alert blocks its transaction journal's delete (measured), so the journals' record alerts are planned and go first; a commitment-rate row (`UsageRatableSumCmtAssetRt`) goes with its ratable summary (measured); a billing period item's lookup to a usage billing period item does not restrict the delete (describe; billing period items cannot be created to measure it, and describe's restricted flag matched each block measured). Then come collection plans and disputes, billing, fulfillment, contracts with their rate card entries, orders (those not in Draft set back to Draft first), assets with their rate card entries, relationships, work orders and cases, quotes with their generated documents and files, and opportunities. Every delete is all or nothing; a row a parent's delete already took counts as deleted. The run rolls back, and the result says nothing was changed and lists nothing as not deleted, when Salesforce refuses any planned record (the result names it, with the status code and a description of it; not the platform's own message, which can name other records the user may not see), when usage rows are still there once the teardown can do no more, when anything else fails, or when a limit is reached part way. One DML statement is kept for the rollback; the savepoint is set before any delete. What the plan leaves out by design is reported as not deleted: a bucket that holds, or is above, another account's entitlement, the account's entitlement account directly above such a bucket, the account's entitlement such a bucket holds, payments, and posted or void debit memos.

### Result

The flow ends on a screen that shows the invocable's result: whether the reset completed, what it removed and what it did not delete, by object, or why it did not run. After a completed reset it also refreshes the active `PricingDiscovery` decision tables through `RLM_Refresh_Decision_Tables_By_Usage_Type`, and the screen shows how many were queued, which failed, or that none matched. That refresh runs as the user who ran the reset, and Salesforce queues one only for a user with Modify All Data and Customize Application. For anyone else, such as the salesrep persona, every table fails to queue, and the screen names that cause and says to ask an admin. A fault in that refresh is shown on the same screen and does not undo the reset; a governor limit hit by the refresh would, because it runs in the reset's transaction and no fault path catches a limit.

| Output | Meaning |
|--------|---------|
| `completed` | Every step ran. False when the run was refused, stopped early or failed, and `reason` says why |
| `cleared` | The run completed and every record it was asked to delete is gone |
| `removedSummary` | What was deleted, by object, such as `Invoices: 3; Credit Memos: 1` |
| `retainedSummary` | What was not deleted, by object, with the reason, such as `Payments: 1 (payments are not deleted: …)` |

Payments are never deleted, because Salesforce refuses to delete a processed payment. A Delete Billing reset of an account with payments therefore completes without clearing it. The same goes for posted and void debit memos: Salesforce refuses to delete them, even with Delete Invoice and Invoice Lines, and a posted one can be voided but not canceled.

### Permission set

`RLM_UtilitiesPermset` grants access to the `RLM_AccountUtilities` Apex class, and what a user needs to delete assets and orders, which the salesrep persona's other sets do not grant: Asset and Order read, edit and delete; Access Lifecycle-Managed Assets (without it, "You can't delete assets that have Lifecycle Management."); Edit Activated Orders and the Activate Orders it depends on, since an activated order is set back to Draft before it is deleted; and Account read, which Asset read depends on, with the Contact read Account read depends on in orgs with person accounts. Activate Orders and Edit Activated Orders also let the holder activate and change activated orders in the UI. Assigned in both `quantumbit` and `tso` flows, and to the salesrep persona in `prepare_personas`. The persona has neither Modify All Data nor View All Data, so it takes the non-admin path. It still cannot read billing, collections or fulfillment records, and cannot delete records other users own, so the reset refuses an account that has any (see *Non-admin path*); on an account whose records the persona owns and can read, it runs in full. `RLM_AccountResetPlan` needs no class access of its own: only the invocable's class is an entry point.

Activated contracts. `RLM_Order_Contract_Creation_and_Association` activates the contracts it creates when an order is activated, and the set does not grant **Delete Activated Contracts**. Measured on tkdef (264, todo 397) as the salesrep persona, runAs, rolled back, on an activated contract it owned: without that permission, `UserRecordAccess.HasDeleteAccess` was false and the delete was refused ("insufficient access rights on object id"); with it, both read true and the delete succeeded. It depends on Activate Contracts and Delete Contract, and Activate Contracts in turn on Read Account, Read and Edit Contract, and Read and Edit Order. A Draft contract the persona owned was deletable without it. So the persona's reset of an account with an activated contract is refused, naming the contract and the permission. The set does not grant it, by owner decision (todo 397, 2026-11-26): such an account is reset by a user with Modify All Data and View All Data, on the admin path.

Measured on a 264 org (todo 397): Allow Revenue Records Deletion lets Draft and Canceled invoices and credit memos be deleted but refuses a Posted invoice ("You can only delete the invoice if it is in Draft or Canceled status."); Delete Invoice and Invoice Lines deletes Draft and Posted invoices, settled or not, but no credit memo. Neither deletes a Posted credit memo or a Processed payment, and Delete Credit Memo and Invoice (`DeleteCrMemoAndInvoice`) is an Order Management permission that a Salesforce user license refuses. Neither is enough on a Minimum Access profile: a user there holding them, with the managed Billing Operations User and Billing Admin sets, was still refused every delete ("DML operation DELETE not allowed on Invoice"), while a System Administrator holding the same sets was not. Which profile permission makes the difference was not isolated.
