# DRO Plans — Author, Load, and Maintain Order Fulfillment

Use this skill to translate an order fulfillment requirement into design-time
configuration, deploy it through CSV/SFDMU and existing APIs, and verify the
runtime plan generated by DRO. It is plain Markdown for any repository agent.

A plan configuration describes how products decompose, which fulfillment steps
apply, and the order those steps run. A runtime plan is the instance DRO creates
for a submitted order. Start with the authoring guide for a new configuration,
the CSV guide for a dataset, or the update guide for an existing org.

The tools have different roles: SFDMU (Salesforce Data Move Utility) loads CSV
records and resolves their relationships; CumulusCI (CCI) runs the repository's
configured tasks; Salesforce CLI (`sf`) inspects and operates on the target org.

## Quick Rules

1. Discover the target org's settings, schema, configuration, and runtime usage
   before writing. Release 264/API 68 is the reference; target evidence wins over
   pre-GA documentation and shipped sample values.
2. Author configuration records, not `FulfillmentPlan` or `FulfillmentStep`
   records. DRO generates runtime records when an order is submitted.
3. Resolve products, groups, steps, providers, users, queues, and attributes by
   verified unique portable keys; stop on ambiguous matches.
4. Load prerequisites and parents before children. Validate decomposition and
   dependency graphs, dependency direction, scopes, and condition resources.
5. For CSVs, read [csv-and-sfdmu.md](csv-and-sfdmu.md) and the
   [SFDMU skill](../sfdmu-data-plans/SKILL.md). Use 5.6.4+, non-destructive matching,
   and a scoped plan rather than copying the whole `qb-dro` dataset.
6. For an existing org, capture before-state and review a field-level delta.
   Explicit clears need verified null semantics; omitted fields mean preserve.
7. Inspect condition JSON and rule-library/context alignment. Verify generated
   rule references and evaluation after creating, changing, or clearing conditions.
8. Read back every intended record and relationship. Report configuration,
   runtime composition, and end-to-end fulfillment verification separately.

## DO NOT

- Do not reload the full sample dataset into a used org to change one plan, or
  delete shared configuration as a shortcut. Follow `AGENTS.md` for destructive
  operation approval; use non-destructive Upsert for new configuration datasets.
- Do not match target records using source-org IDs or autonumber Names. Do not
  write internal RuleSet artifacts directly to manufacture condition wiring.
- Do not use `$$` composite notation in lookup-reference CSV columns. It is
  valid only for the matching columns described in the SFDMU skill.
- Do not assume creating a context extension selects it in DRO settings, that
  a custom tag is String because its value looks like an ID, or that credentials
  exist merely because an integration provider was deployed.
- Do not patch runtime states with ordinary DML, assume design edits retrofit
  in-flight plans, or force completion/override Point of No Return without
  authorization for that concrete runtime action.
- Do not report a loader exit, simulation, stable counts alone, or a generated
  plan as proof that external callouts and manual fulfillment completed.

## Workflow and References

Start by resolving the target and requested behavior. Ask only for requirements
that discovery cannot answer: products/actions, required fulfillment outcomes,
scope/assignment choices, or permission to perform a specific out-of-scope action.
Honor authorization already supplied; preparing CSVs does not itself authorize
loading a production org or submitting test orders there.

Read supporting files when their task applies:

| Reference | Read when |
| --- | --- |
| [objects-and-relationships.md](objects-and-relationships.md) | Selecting objects, lookup fields, natural keys, or runtime evidence |
| [authoring-and-deployment.md](authoring-and-deployment.md) | Designing a new configuration or verifying target prerequisites |
| [csv-and-sfdmu.md](csv-and-sfdmu.md) | Creating/exporting datasets, loading, simulation, or repeat-load checks |
| [updates-and-runtime.md](updates-and-runtime.md) | Updating used configuration, clearing/removing fields, or handling in-flight work |
| [examples-and-grounding.md](examples-and-grounding.md) | Following the repository example, checking documentation, or recording evidence |

Produce a concrete change description: target identity/release, configuration
roots and keys, intended records/relationships, prerequisites, field changes,
load sequence, expected runtime result, and verification status. For an update,
also record shared consumers, affected active requests, and recovery boundaries.

## Examples

- **New CSV plan:** "Create a two-step technical-product fulfillment plan for
  SKU `<sku>` in `<target>`." Follow the worked CSV example, resolve the product,
  simulate, load when authorized, and inspect the generated order plan.
- **Targeted correction:** "Make `<step>` a manual task and remove its provider."
  Capture the record, inspect consumers and step-type constraints, apply the
  explicit provider clear, and verify both field values and new plan composition.
- **Existing workflow extension:** "Insert a readiness milestone before
  provisioning." Check dependency scope and cycles, update the intended edges,
  preserve shared/in-flight behavior, and verify the new predecessor relationship.
- **Decomposed order products:** "Make each services line generate a Project
  Service fulfillment item." Follow [decomposed line items](authoring-and-deployment.md#decomposed-line-items)
  and the [CSV extension](csv-and-sfdmu.md#worked-decomposition-extension).
  Create or resolve the technical destination, add its source rule, and bind the
  intended step group without composing the same work twice.
